Write something coherent about threading -- can events safely be handled concurrently with
operator commands? If operator commands do nothing if enabled, it should mean we only need
to consider the interaction between enable/disable and the recorder API. What if the recorder
API for a given table is used from more than one thread? We should probably explicitly
prohibit this, or at least say that done() can only be called from a single thread.
Do we need to make something atomic to allow concurrent writes?

Another option is to make one-shot only selectable at compile-time: this would make
code more efficient, since the rollover mode wouldn't need to set 'stopped'.
Could I have 3 Record_table classes: oneshot, rollover, and selectable-at-runtime?

Manager commands could return more detailed error than 'command failed on 1 or more tables', or
report using the existing dump_name_callback, whose name could be changed to indicate more general
use.
Use of noexcept where applicable.

In unit test, check that dump works correctly, by passing a callback
that writes the output data somewhere the test can verify it.

Measure unit test code coverage.
